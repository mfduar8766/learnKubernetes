What is k8s:
    Container orchistration framework that manages containers (Docker)
    Managed in physical, virutal, or cloud envs
    Became popular because of microservices

Features:
    High Availability: Zero downtime
    Scalability: Apps can be scaled up/down depending on load
    Disaster Recovery: Backups for cases where nodes die

Architecture:
    Master Node: 
        Main K8s process.
        API Server: A container that is the entry point to the k8s cluster. Process different kubernetes clients will talk to
        Controller Manager: Keeps an overview of the cluster IE: if a container needs to be restarted etc.
        Schedular: Responsible for scheduling containers on worker nodes based on workload and available server
            resources on each node.
        ETCD: Backup for the cluster using key value storage in case anything goes wrong. Holds config data, state, ETC.
            You need to manually do the backup storage as k8s does not do this for you.
        Virtual Network: Enables all nodes to talk to each other. Spans all the nodes that are part of cluster.
            Turns all nodes in cluster into one machine that has the sum of all resources of individual nodes.
    Worker Nodes:
        Have kubelet process running on each node that allows clusters to communicate with each other.
        Where the applications are running like docker containers.
    Cluster:
        Combination of all nodes

Components:
    Node: Server physical/virtual machine. Main component of k8s. Each Node has multiple Pods running on that node.
        It does this by installing 3 processess in every node.
        1st. Container runtime: (Docker).
        2nd. Kubelet: Schedular for the pods and containers. Interfaces with the container runtime and the node.
            It is responsiible for starting a pod with a container inside and assigning resources from that node to that container.
        3rd. Kube Proxy: Responsible for LoadBalancing from pods to pods.

        Master Node: Responsible for scheduling, monitoring, and restarting pods, join a new node.
            1. API Server: When you want to deploy a new app in the cluster this is a cluster gateway which gets requests
                to the cluster. Acts as gatekeeper for authentication. 
                Example some request->API Server->request validation->other processess->pod
            2. Schedular: API Server -> validate request and sends it to Schedular. THis will start the pod on a worker node.
                Determines what node to schedule it  in. hecks the resources the app needs and goes through worker nodes to 
                check for available resources and schedule the new pod on that node. It does not execute the scheduling. 
                Kubelet gets the request from Schedular and executes that request on the node.
            3. Controller Manager: Detect state changes of pods (crashing/dying) it tries to recover the state. 
                Makes a request to Schedular to restart pods.
            4. ETCD: This is the cache for the cluster state.

        Pod: Abstraction over a container. Creates a running env (layer) on top of the container. 1 application per pod.
            k8s offers its own virtual network where each pod gets its own IP. Pods can talk to each other
            through the IP which is internal. Pods get a new IP on re creation. Due to this we have Service/Ingress.
        Service: Permanent IP address that can be attached to each pod. Is also a LoadBalancer.
        Ingress: The request goes to ingress and forwards it to the service.
        ConfigMap: External configuration of your app. Contains configs like DB_USER, URLS, ETC. This is connected to the pod.
        Secrets: This contains secrets like DB_PASSWORD usually stored as bas64. Secrets are not encrypted so you need to handle that.
            You can use the data in ConfigMap/Secrets as ENVs in your app.
        Volumes: Allows for persistance of data. Attaches a physical storage on a harddrive to your pod on your local machine
            or remote storage (cloud storage). This is external to the k8s cluster. k8s does NOT manage data persistance.
        Distributed Systems: Replicate all the pods on multiple servers.
        Deployment: A bluePrint of the pods. Specify replica sets of pods. Abstraction on top of pods.
            Database cannot be replicated through deployment because DB has state and each replica would have its own state.
        StateFulSet: Specific for apps like DBS this allows management of replicas of DBs. 
            Deployment is not easy so Dbs should outside of cluster.

How to create pods/services:
    K8S Configuration: All configuration goes through the master node with a process called API Server.
        Every config file has 3 parts (MetaData, Specs, Status (automatically created/managed by k8s))
        Status of the pod comes from ETCD.

ConfigMap && Secrets need to be created before deployments       

Config File: Has 3 parts to a config file.
    1. MetaData: Deployment MetaData
        name: Deployment name
        labels: Unique identifier for the deployment. Multiple replicas get unique name but share the label.
    2. Specification: attributes will be specific to the kind of component you are creating
    3. Status: Automatically managed by k8s

Resource Quota: Limits the amount of memory a container can use in a pod. You need to apply a config to do this in your cluster.
    Then use <kubectl top nodes> <kubectl top pods -A> to get the metrics for the cluster.
    Example:
        Here Pod1 has req: 100 limit: 200. Currently used request is 100/400 and currently used limit is 200/500
        After adding another pod smae specs request currently used is 200/400 and limit is 400/500
        NameSpace:
            Pod1:
                request: 100mb
                limit: 200mb
            Resource Quota:
                requests.memory: 400mb Can only use this much of memory
                    currently used: 100mb
                limits.request: 500mb
                    currently used: 200mb
            Pod1:
                request: 100mb
                limit: 200mb
            Resource Quota:
                requests.memory: 400mb Can only use this much of memory
                    currently used: 200mb
                limits.request: 500mb
                    currently used: 400mb
    Requests:
        Guaranteeing your Pods containers have a certain amount of resources. 
        The containers NEED AT LEAST this amount of resources or they will starve.
    Limits:
        This is the maximum your pods container can consume before its killed off
    Containers:
        You can specify resource limit on containers
            Example:
                containers:
                - name: foo
                    image: bar
                    resources:
                    requests:
                        cpu: 250m -> 250 millacore of cpu usage
                        memory: "65M" -> 65MG
                    limits:
                        cpu: 500m -> MUST BE AT LEAST SAME AS requests
                        memory: "130M"

Probes:
Liveness vs. Readiness (The Big Distinction)
This is where most people get tripped up. Think of it like a restaurant:
    Ways to check Liveness && Readiness (HttpGet/TcpSocket most common):
        1. httpGet: Hits an endpoint. A response code between 200–399 is a "success."
        2. exec: Runs a command inside the container (e.g., cat /tmp/healthy). If the command returns exit code 0, it's a "success."
        3. tcpSocket: Checks if a specific port is open. If the TCP connection is successful, it's a "success."
    Parameters:
        1. initialDelaySeconds: How long to wait after the container starts before checking.
        2. periodSeconds: How often to perform the check.
        3. failureThreshold: How many consecutive failures before K8s gives up and kill the container.
        4. successThreshol: Only needs 1 success to be put back in rotation.
            Liveness: MUST ONLY BE 1
            Readiness: Can be greater than 1
        5. timeotSeconds: How long we give the container to respond
    Liveness Probe: Checks if the container is still running. If this fails, K8s restarts the container.
    Readiness Probe: Checks if the container is ready to accept traffic.
        If this fails, the Pod is removed from the Service's load balancer so users don't hit an error page.
    Startup Probe: Disables liveness and readiness checks until the container has fully started. This is great
     for "slow-starting" legacy apps.

Services:
    The Three Ports Explained
    Port Name	Where it lives  Who uses it?
    nodePort	The Worker Node's IP. External Users. They hit http://<Node-IP>:30000.
    port	    The Service's Internal Cluster IP. Other Pods in the cluster. They hit http://ui-service:3000.
    targetPort	The Pod's IP. The Service. It forwards traffic here. It must match your containerPort in the Deployment.
        NOTE: If targetPort is NOT defined K8S will use sane value as port.

The Breakdown: port-forward vs. NodePort
    1. kubectl port-forward (The Tunnel)
        When you run $K8S_CMD port-forward svc/ui-service 3000:3000:
        Local Port (3000): Your laptop starts listening on 127.0.0.1:3000.
        Service Port (3000): It connects to the port defined in your Service YAML.
            The Result: Traffic goes from your machine → Kube-API Server → Service → Pod.
        NodePort status: It is completely ignored. You could set nodePort: 32000 or delete it entirely, and port-forward would still work.
    2. NodePort (The Front Door)
        If you don't use port-forward, you access the app using the nodePort you defined:
        URL: http://<worker-node-ip>:30000
        The Result: Traffic hits the actual physical (or virtual) IP of your Kubernetes node on that specific high-range port.
        Use Case: This is how "real" external traffic enters the cluster if you don't have a cloud LoadBalancer.

NodePort vs LoadBalancer:
                   NodePort	                                        LoadBalancer
How you access it: http://<Node-IP>:30000	                        http://<Cool-Unique-Name>.com or a Static IP
Port: Must be in the high 30000+ range	                            Can be standard Port 80 or 443
Infrastructure:	Uses the existing Worker Nodes                      Creates a new cloud resource (costs money!)
Reliability:	If that specific Node goes down, the URL fails	    High Availability; it tracks all nodes automatically

How the Traffic Flow Changes
With NodePort:
    User → Specific Node IP:30000 → Service → Pod
    Problem: If you have 10 nodes, which IP do you give your users?
    If that node dies, your app "disappears" for the user even if the other 9 nodes are fine.
With LoadBalancer:
User → Load Balancer IP (Port 80) → All Nodes (NodePort) → Service → Pod
    Solution: The Load Balancer acts as a single "Front Door." It sits in front of all your nodes.
    If Node A dies, the Load Balancer just sends traffic to Node B.

NameSpaces: Used to organize resources in a cluster. LIke a virtual cluster inside the existing cluster.
SHOULD NOT USE FOR SMALLER PROJECTS
    Can be created with the commands or using a config file.
        CMD: 
        kubectl create namespace <NAME>
        kubectl delete nameSpace <NAME>
    Each NameSpace MUST have its own configMap/secret for a shared resource.
        Example:
            NameSpace A have a configMap/secret to the DB NameSpace B wants to also use the DB,
            NameSpace A && B need to have independent configMaps/secret to reference the DB.
    NameSpaces CAN SHARE services
    Some components are NOT nameSpace specific they are global:
        Volumes/persistent Volumes
    When to use NameSpaces:
        1. When theres to many resources example to many services/deployments/replicas/configMaps
            Can have a Db nameSpace or a Monitoring nameSpace for prometheus graphana etc.
        2. Multiple teams same application. Example two teams have same deployment name and one team deploys a new version.
            This will override team 1s deployment.
        3. Resource sharing IE: development/staging clusters.
        4. Using Blue/Green Deployment, which means in same cluster you have 2 different versions of production
        5. Access and Resource Limits: 2 teams and each team can only use their own namespace and not touch others.
            Define CPU/RAM each NameSpaces can use.
1. Kube System: Do NOT create/modify this.
    Holds system procesases
    Master and kubectl processes
2. Kube Public: Holds publicly accessible data.
    Has a configMap that contains cluster information that is accessible without authentication. Example: kubectl cluster-info command.
3. Kube Node Lease: Holds information on the heartBeats of nodes.
4. Default: Used as default nameSpace for resources.

Ingress Vs External Service: 
    Generally External Service should only be for testing. Example K8s cluster has a UI app.
    UI.App -> UI.Service (This uses an external port to expose the UI to the user). For testing.
        http://127.0.0.1:333
    UI.App -> UI.Service (Becomes Internal Service ClusterIP) -> UI.Ingress.
        Flow: Request -> UI.ingress -> UI.Service -> UI.App
        https://myApp.com
For ingress you need a ingressController (Install ingress pod in your cluster) along with the .YAML file.
IngresController: Handles processing and evaluation of ingress rules and is the entry point to the cluster.
To install ingress you need to run: minikube addons enable ingress
    This installs K8S implimentation of Nginx Ingress Controller

The "Traffic Map"
    You go to http://myapp.com in your browser. (The browser assumes Port 80).
    Minikube Tunnel receives that on Port 80 and hands it to the Ingress Controller.
    Ingress Controller looks at your YAML and says: "Aha! This goes to ui-service on Port 3000."
    ui-service receives it on 3000 and sends it to your Container on 3000.

Helm: Package manager for k8s. Its also a template engine.
Structure:
    myChart/
        chart.yaml -> Contains metadata about the chart
        values.yaml -> Contains all the values for the templates. These default values can be changed
        charts/ -> Holds dependencies that this chart depends on

    Helm V2: Installation comes in 2 parts
        Helm Client (CLI)
        Server (Tiller)
        When you run helm install myChart helm sends the files to Tiller and Tiller 
        executes the request and creates components from the YAML files in the cluster.
        When you create/change deployment Tiller will store a copy of that config for future reference.
        Example:
            Changes will be applied to existing deployment instead of removing it and making a new one
            If it fails you can roll back that upgrade (hrlm rollback <CHART_NAME>)
            1. installed chart (helm install <CHART_NAME>)
            2. upgrade to version 1.0.0 (helm upgrade <CHART_NAME>)
    Helm V3: No Tiller only helm binary executable

Container Communication Inside Pod (Networking):
    Pod Fundamental Process: 
        Each pod has its own IP. This IP is reacheable fron all other pods in the cluster.
        Has at least 1 container and its own unique IP.
        When a Pod is created on a Node it gets its own NameSpace and its own virtual ethernet connection.
        So a Pod is a virtual host like your PC. Both have IPs and a range of ports to allocate to its containers.
    Container Port Mapping without Pods: How to allocate pors without conflicts
        Example: PostgreSQL container running of port 5432. When you start a container directly in your machine
        you bind your host port to that container port. (<HOST_PORT:CONTAINER_PORT>) 
        So (5000:5432) 5432 gets mapped to host 5000.
    Multiple Containers 1 Pod:
        Since the Pod is a virtual host containers can talk to each other over 127.0.0.1:<PORT>
        Each container gets a Pause Container (Sandbox Contaienr): Used to reserves and holds network namespace
            Thats shared by all containers in a pod. If a container dies Pause stays alive. 
            If Pod gets deleted Pause is gone.

Volumes:
    MOUNT PATHS OVERRIDE EXISTING DIRECTORIES IN A CONTAINER
    Is a directory with some data
    K8S does not give data persistence out of the box. Must be configured for each app.
    Pods access storage by using PVC as a Volume.
        Pod->PVC->finds a volume in cluster that satisfies the PVC->volume creates the storage resource.
        Volume is than mounted into the pod and than mounted into the container inside the pod.
    Requirements:
        1. Storage should not depend on pod lifecycle. Pod depends on storage.
        2. Storage must be available on all nodes.
        3. Storage needs to survive even if cluster crashes.
    Persistent Volume:
        It is not nameSpace specific.
        You decide what type of storage your cluster needs.
        A cluster resource like RAM/CPU that is used to store data. 
        It uses the local hardrive (from cluster nodes), cloud storage, nsf server.
    Persistent Volume Claim: (PVC):
        Claims a Volume with certain capacity. Must exist in same namespace as pod using the Claim
    Volume Types (Local/Remote/ConfigMap/Secret):
        Local: Violates 2nd/3rd rule of persistence for databases
        Remote:
        ConfigMap: Local volume not created via pv && PVC managed by k8s
        Secret: Local volume not created via pv && PVC managed by k8s
    Storage Class:
        Creates/provisions PV dynamically when PVC claims it.
        Abstraction level that abstracts the storage provider and its parameters. It is claimed by the PVC.
        Pod -> claims storage via PVC -> PVC requests storage from Storage Class -> Storage Class creates PV (Persistent Volume)
    Example:
        containers:
        - name: mongodb
          image: mongo:latest
          ports:
            - containerPort: 27017
          envFrom:
            - secretRef:
                name: mongo-secret
            - configMapRef:
                name: mongo-config
          volumeMounts:
            - name: init-data-volume
              mountPath: /data/init # Where the JSON file sits THIS WILL OVERRIDE EXISTING DIRS IN A CONTAINER SO IT MUST BE UNIQUE
            - name: mongo-storage # Where the actual DB lives
              mountPath: /data/db/file.txt > This saves the file to the /data/db dir instead of overriding the whiole dir
              subPath: file.txt > SUB_PATH
                For example lets say mountPath is /data/db/file.txt. We use subPath to write a subPath to just the file.txt 
      volumes:
        - name: init-data-volume
          configMap:
            name: mongo-init-data # The JSON from ./start.sh script
        - name: mongo-storage
          persistentVolumeClaim:
            claimName: mongo-pvc # The persistent storage
